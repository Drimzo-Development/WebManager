# Security architecture

## Assumptions

The administrator is trusted. **Website code is not**: a compromised or malicious website must not reach the host, the
dashboard, the database, the Docker daemon or other websites.

## Layers

| Risk | Measure | Where |
|---|---|---|
| Access to the Docker daemon | The socket is mounted only in the `agent` container; the agent listens only on the internal network `wm-mgmt`; no free Docker arguments, only validated actions (`agent/src/validate.js`) | `docker-compose.yml`, agent |
| Compromised dashboard | The dashboard only owns the *dashboard* token (read + file manager + requesting a console ticket). Creating, starting or deleting containers needs the *worker* token (403 + audit entry). With the dashboard token an attacker cannot open a shell by default (only the worker may ask for console tickets); with `CONSOLE_TICKETS=dashboard` the dashboard token can, which is about the same reach as writing files into a website | agent |
| Arbitrary images | Allowlist `templates/runtimes.json`, fixed tags, optional digest; no user Dockerfiles | agent |
| Container breakout | `cap_drop ALL`, `no-new-privileges`, `read_only`, non-root UID per website, PID/memory/CPU limits, no `privileged`, no host mounts except the website's own project directory | `sites.js`, `jobs.js` |
| Lateral movement | One Docker network per website; only the proxy is attached. No access to `wm-mgmt`/`wm-db` | agent |
| File access | Operations run with the UID of the website (`spawn uid/gid`), every path component is checked with `lstat`, symlinks are rejected, `O_NOFOLLOW`, `..`/absolute paths forbidden | `fsworker.js` |
| Secrets | `.env` is 0600; website environment variables are AES-256-GCM encrypted (key `APP_KEY`), the env file of a website is 0600 root (passed with `--env-file`, not mounted); passwords never appear in arguments or logs | installer, PHP, agent |
| Dashboard attacks | Argon2id, sessions (HttpOnly, SameSite=Strict, Secure under HTTPS, idle/absolute timeout, UA binding), CSRF token + origin check, login throttling, CSP `default-src 'self'` without inline scripts, `disable_functions`, `open_basedir` | `app/` |
| Proxy misconfiguration | A new route is written atomically, checked with `nginx -t` and rolled back on error; upstreams are resolved at request time | `proxy.js` |
| Users and roles | Roles administrator/operator/viewer; permissions are checked centrally per route (`app/Http/Permissions.php`, default = operator), role/status/password are checked against the database on every request; at least one active administrator always remains | `app/` |
| Passkey sign-in (passwordless) | Only with user verification (the UV flag is enforced so that possession + device PIN/biometrics are two factors), challenge from `random_bytes` bound to the session (5 minutes), account and key via the globally unique credential ID, user handle (HMAC of APP_KEY) is checked, disabled accounts rejected, throttling per IP, audit entries | `PasskeyLoginApi.php` |
| Passkeys (WebAuthn) | Own verification in PHP (`WebAuthn.php`, `Cbor.php`, `openssl_verify`): challenge per operation, **origin and RP ID hash** are checked against the dashboard domain (phishing protection), type `webauthn.create`/`get`, user presence, ES256/RS256 signature, **signature counter** (clone detection), `crossOrigin` rejected, registration only without attestation (`none`), strict CBOR decoder with limits; adding/removing needs the password; not usable without HTTPS/domain | `WebAuthn.php`, `Cbor.php`, `AccountApi.php` |
| Two-factor authentication | TOTP (RFC 6238, tested with the test vectors), secret AES-256-GCM encrypted, every code only once, throttling per user, recovery codes with 80 bit stored as SHA-256; changes need the password; the session is only created after the second factor | `Auth.php`, `Totp.php`, `AccountApi.php` |
| Database per website | Only on request; own container in the private website network without published ports, `cap_drop ALL` (only what is needed to start), `no-new-privileges`, memory/PID limits; credentials random and stored AES-256-GCM encrypted, never in arguments; dumps in `sites/site-NNN/dumps` (0700, not in the web root); images only from the allowlist; external access only optionally via a forwarder container with an allowlist (deny by default, `0.0.0.0/0` rejected) | `database.js`, `DatabaseApi.php` |
| Database management (Adminer) | Only on request, container in the private website network, no published port; reachable only through the dashboard vhost with `auth_request` against the dashboard session (at least operator); switches off after 30 minutes | `database.js`, `proxy.js` |
| Security headers and WAF | Headers from strictly validated values (CSP from a narrow character set only); WAF rules as nginx `map` with regex, tested against the documented nginx escape pitfalls; changes pass `nginx -t` with rollback | `waf.js`, `proxy.js` |
| Updates from the dashboard | Containers execute nothing on the host: the agent writes (only with the *worker* token, audit entry) a file `update/request` containing `check` or `update X.Y.Z`; a systemd path unit starts `scripts/update-helper.sh`, which validates the request again and only calls the regular `update.sh` (SHA-256/optional GPG, backup, health check, rollback, never a downgrade) with a fixed version. Release texts are shown as text only (truncated, links only `https://`). Administrators only; can be switched off with `UPDATE_HELPER=off` | `update-helper.sh`, `update.js`, `UpdateApi.php` |
| Proxy error pages | Static files in the proxy image for 400/403/413/429/500/502/503/504; no scripts and no external resources; reveal no internals | `proxy.js`, `docker/proxy/errors/` |
| Websites reaching the host | Optional (`install.sh --harden-egress`): iptables rules for the website network pool only – new connections to the Docker host and to link-local/metadata addresses are dropped, optionally private networks too (`EGRESS_BLOCK_PRIVATE=1`); the internet stays reachable | `egress-guard.sh` |
| Mandatory 2FA | Setting “optional / administrators / everyone”; affected users without 2FA can only reach *My account* and sign-out; emergency switch `bin/console security:require-2fa off` | `Auth.php`, `SystemApi.php` |
| External backups | Upload only **encrypted** (gpg AES-256); credentials of the target (`rclone.conf`) and the passphrase stay root-only on the host; dashboard actions are a fixed list; file names on the target are checked against a fixed pattern; the restore test imports into a throw-away container without network | `backup-remote.sh`, `backupctl.js` |
| Cron jobs | Commands run only in the same isolated throw-away container as the website commands; expression and command are validated server side; execution only through the worker queue; no parallel double run; at most 20 per website; all changes are audited | `CronApi.php`, `cron.js`, `jobs.js` |
| Automatic updates | Off by default; patch versions of the same major/minor line only, within a time window, at most one attempt per 20 hours, paused after a failure; the host helper decides on its own | `update-helper.sh`, `update.js` |
| Storage cleanup | Fixed category list with fixed rules; the dashboard can only send category names; candidates are recalculated on execution; paths come from directory listings with strict name patterns | `storage.js`, `StorageApi.php` |
| Roll back to the previous version | The host helper only receives the word `rollback` and selects the backups of the last update itself; dashboard: administrators only, after typing `ROLL BACK`; the current state is dumped first; on any error the original state is restored | `rollback.sh`, `update-helper.sh` |
| Statistics | No IP addresses on disk (only short-lived salted identifiers for visitor counting, deleted after 2 days); query strings are not stored | `metrics.js` |
| Country rules | Allocation lists of the five regional registries via https as nginx `geo` maps per website; country codes strictly `[A-Z]{2}` | `geo.js`, `proxy.js` |
| Attack protection | Automatic/manual IP bans as nginx `geo` map (answer 444), evaluation of the proxy access log in the agent, configurable thresholds and exceptions | `protect.js`, `nginx.conf` |
| Password protection of websites | `auth_request` in the proxy; cookie = HMAC (key from `APP_KEY`) bound to website and password; Argon2id hashes; throttling; redirect target local paths only | `GateController.php`, `proxy.js` |
| Traceability | Agent audit log (`/var/log/webmanager/agent-audit.log`), dashboard table `audit_log` (administrators only, searchable, CSV export that neutralises spreadsheet formulas, kept one year) | agent, PHP |
| Web console | Administrators only (central permission rules, session only, no API tokens, CSRF). **Off per website** until switched on. Requires an account with a second factor and a **fresh password (and TOTP) confirmation** (10 minutes, throttled, TOTP codes single use) even in a valid session. The browser gets a random one-time ticket (256 bit, 30 seconds) that is sent as WebSocket subprotocol, **never in a URL or log**; by default only the **worker** may ask the agent for tickets (`CONSOLE_TICKETS=dashboard` changes that), so the dashboard token cannot open shells. The reverse proxy forwards `/__console` to one fixed agent path only after the dashboard confirmed an administrator's session and the Origin of its own page (`auth_request`). The agent runs `docker exec` with a TTY through the Docker API (fixed command, no user input in it), limits sessions (3 per website, 6 in total), ends idle (15 minutes) and long (2 hours) sessions, and audits open/close without ever recording input. Sessions end at once on sign-out, password change, deactivation, demotion, deletion or switching the console off; a worker sweep every 30 seconds ends the sessions of accounts that are no longer active administrators as a backstop. The terminal page has its own policy (inline styles allowed for the terminal library, no inline scripts; framing only by the dashboard); the rest of the dashboard keeps the strict policy. `CONSOLE=off` removes the feature | `console.js`, `ws.js`, `ConsoleApi.php`, `ConsoleGuard.php`, `proxy.js` |
| Application templates | The catalog is data (`templates/apps.json`), the steps are fixed code (`workers/src/apps.js`): downloads only from the vendor over https, verified with the vendor's checksum before unpacking, run in the same isolated throw-away container as other commands. No secrets in generated files: the application reads the database settings from the environment | `apps.js`, `SiteService.php` |
| Availability checks | The agent asks websites through `docker exec` in the proxy container (`wget --spider`, fixed arguments, no shell, container name and port from the stored specification); only the status is evaluated, a result that cannot be understood counts as “unknown”, never as an outage | `probe.js` |
| Supply chain | The Docker repository key fingerprint is checked; release download only over https with mandatory SHA-256, GPG signature against `keys/release.asc` of the installed version (mandatory once the key is shipped); fixed image versions | `install.sh`, `update.sh` |
| Known vulnerabilities in images | Fixed versions, `apk upgrade` at build time, no npm in agent/worker, scan with `scripts/security-scan.sh` (Trivy), run in the CI on every push and weekly for the stack images and the third-party images | Dockerfiles, `scripts/` |

## Residual risks (honestly)

* Whoever owns the *worker* token or the Docker socket is effectively root on the host. The agent reduces the attack surface but does not replace host protection.
* The agent runs as root in its container (needed for the socket, `chown` and UID switching); its capabilities are limited to CHOWN/DAC_OVERRIDE/FOWNER/SETUID/SETGID.
* The custom install/build/start command runs as a shell command in the (isolated) website container – intended, limited only by container isolation.
* The CI scans the images of this tree strictly and the third-party images (database, Node.js and Python runtimes, Adminer) as a warning: only their maintainers can fix findings there. Keep the pinned versions in `templates/runtimes.json` current; the Node.js 20 runtime is end of life and has no newer Alpine image, so move websites to 22 or 24.
* The official database images contain `gosu`, a Go binary that only drops root privileges while the container starts (it never listens). Its Go standard library findings can only be fixed by the image maintainers; `scripts/security-scan.sh` leaves this one file out so that real findings stay visible. Check again whenever the database image is updated.
* Kernel vulnerabilities: the kernel is shared. For tenants that do not trust each other use separate hosts or a sandbox runtime.
* Outgoing traffic of websites to the internet is allowed. Access to the Docker host and metadata services is **not** blocked by default; the optional egress guard (`--harden-egress`) closes it.
* Behind another reverse proxy the visitor address is the proxy's address unless `TRUSTED_PROXIES` is set; set it to the proxy's addresses (never to addresses you do not control), otherwise throttling, bans and rate limits treat all visitors as one.
* Dashboard in the unencrypted IP mode: password and session cookie travel in clear text until a domain with HTTPS is set up. The dashboard warns but does not enforce HTTPS.
* Offline updates (`update.sh --file ARCHIVE --sha256 HASH`) and an installation that bootstraps through `install.sh` without `--sig-url` verify the SHA-256 only, not the GPG signature: the administrator supplies the checksum, so take it from a trusted source and verify the signature by hand as described in the README. Updates fetched by `update.sh` or the dashboard always check the signature against `keys/release.asc` of the installed version.
* The proxy trusts an `X-Forwarded-Proto: https` sent by a client to mark a request as HTTPS (needed behind a TLS-terminating proxy in front of WebManager). A client can therefore only influence its own response (cookie flag `Secure`, HSTS header); it cannot affect other visitors.
* The worker has outgoing network access (network `wm-egress`) only to send notifications (SMTP server, and the https addresses of webhook, ntfy and Telegram that an administrator entered). It still has no Docker access. Webhook/ntfy addresses must be https with a full domain name and no credentials; targets inside the server (loopback, link-local, cloud metadata) are refused when saving and at connect time, redirects are not followed. Addresses, secrets and tokens are stored encrypted. Private LAN addresses are allowed on purpose (a ntfy server in your own network).
* Without mandatory 2FA, 2FA is optional per user; an account without 2FA and a leaked password is unprotected. Recommendation: make it mandatory for administrators.
* The WAF is pattern matching: it can be bypassed (encoding tricks, attacks in the request body) and produces false alarms. It complements, but does not replace, current software and secure programming.
* Database containers run with the rights needed to start and as root during initialisation; they share the kernel with the host. Whoever can run commands in the website container can connect to the database with its credentials – intended.
* Published Docker ports (external database access) bypass the host firewall (ufw). The barrier is the allowlist in the forwarder. The database connection is unencrypted.
* Country rules rely on the registration country; they are no proof of identity and easy to bypass with a VPN/proxy.
* Attack protection does not stop volumetric DDoS attacks and can hit legitimate visitors behind a shared address – therefore off by default with an exception list.
* IP rules see the address that talks to the proxy; behind a CDN/load balancer they are ineffective.
* Password protection and maintenance mode are enforced by the proxy; whoever reaches the website container directly bypasses them. The website networks are separated; only the proxy is attached.
* Custom nginx configurations only act inside the website container but can change its behaviour arbitrarily.

## What remains – and why

The remaining points are not configuration errors but properties of the architecture or limits of the technology; they can only be narrowed down:
the agent needs the Docker socket (root equivalent), websites share the kernel, custom commands intentionally run in the container, WAF and country rules are heuristics, and volumetric DDoS attacks can only be fought in front of the server.
Recommendations for operation: mandatory 2FA for administrators, HTTPS for the dashboard, `--harden-egress`, a host with automatic security updates, separate hosts for untrusted tenants.
